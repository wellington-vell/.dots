# AGENTS.md

Guidance for AI agents and contributors working in this repository.

## What this is

A NixOS flake organized around the [Dendritic pattern](https://github.com/mightyiam/dendritic),
powered by [flake-parts](https://flake.parts/) and [import-tree](https://github.com/denful/import-tree).

The core idea: **every Nix file except entry points is a flake-parts module** (a "feature").
Each file implements one feature across every configuration it applies to. Lower-level
configurations (NixOS, home-manager, ...) are stored as `deferredModule` values under the
`flake.modules.<class>.<name>` option, and files merge under shared names.

There are no manual import lists. `imports.import-tree ./modules` recursively loads every
`.nix` file under `modules/` as a flake-parts module, so files can be added, removed,
renamed, or moved freely. Files/dirs starting with `_` are ignored by import-tree (used as
an opt-out when needed).

## Layout

```
flake.nix                              entry point: flake-parts + import-tree
flake.lock
modules/                               every *.nix here is a flake-parts module
├── flake-parts.nix                    imports flake-parts.flakeModules.modules (declares flake.modules)
├── nix.nix, boot.nix, network.nix,    one feature per file, each merging into
├── locale.nix, packages.nix,          `flake.modules.nixos.base`
├── users.nix, state.nix
└── hosts/
    └── well.nix                       host "well": composition + nixosConfigurations
hosts/
└── well/
    └── hardware-configuration.nix     generated by nixos-generate-config (ignored by import-tree)
```

### Entry points (exceptions to the pattern)

- `flake.nix` — flake entry point, must stay as-is.
- `hosts/well/hardware-configuration.nix` — machine-generated by `nixos-generate-config`.
  It lives outside `modules/` so import-tree never treats it as a flake-parts module. It is a
  plain NixOS module, referenced explicitly in `modules/hosts/well.nix` via `imports`.

## How modules merge

Each feature file contributes to the `flake.modules.nixos.base` deferred module. The Nixpkgs
module system merges all definitions under that name.

```nix
# modules/boot.nix
{
  flake.modules.nixos.base =
    { pkgs, ... }:
    {
      boot.loader.systemd-boot.enable = true;
      boot.kernelPackages = pkgs.linuxPackages_latest;
    };
}
```

Note the `{ pkgs, ... }:` — this is a *NixOS* module (the deferred module body), evaluated in
the NixOS context, not at the flake-parts top level. Do not reference `pkgs` in the outer
flake-parts module; it is not available there.

### Hosts

A host file both composes the host and exposes it as a flake output:

```nix
# modules/hosts/well.nix
{
  config,
  inputs,
  ...
}:
{
  flake.modules.nixos.well = {
    imports = [ ../../hosts/well/hardware-configuration.nix ];
  };

  flake.nixosConfigurations.well = inputs.nixpkgs.lib.nixosSystem {
    modules = with config.flake.modules.nixos; [
      base
      well
    ];
  };
}
```

Host-specific NixOS settings merge into `flake.modules.nixos.well` under the host's own name
(still a deferred module), and the host is the one place that decides which features
(`base` + anything else) it needs. See the `flake.modules` option declaration in
`flake-parts`' `extras/modules.nix` for how the values become `_class`-tagged modules.

## Rules of thumb

- **One feature per file.** If a file grows, split it into more feature files, don't bolt on
  unrelated settings.
- **Importing a module should enable the feature.** Prefer defining the enabling config
  directly over adding `enable` options (see the the dendritic "anti-patterns" doc).
- **Share values via the top-level config**, never via `specialArgs` pass-through.
- **Name files after the feature**, not after the config class (`nix.nix`, not
  `nixos/nix-configuration.nix`). Paths are free-form; only the feature they express matters.

## Common tasks

### Add a system package

Edit `modules/packages.nix`, appending to the `environment.systemPackages` list. Rebuild with
`nixos-rebuild switch --flake .#well`.

### Add a new feature

1. Create `modules/<feature>.nix` defining `flake.modules.nixos.base = { ... };`.
   import-tree picks it up automatically.

### Add a new host

1. Create `modules/hosts/<name>.nix` modeled on `well.nix`.
2. Generate machine specifics: `sudo nixos-generate-config --dir hosts/<name>`.
3. Point its `flake.modules.nixos.<name>` at `../../hosts/<name>/hardware-configuration.nix`.
4. Add whatever features it needs to the `modules` list.

### Disable a feature temporarily

Prefix the file or directory with `_` (e.g. `_glyphs.nix`) — import-tree ignores it.

## Verification

```console
nix flake check          # evaluates all outputs, including nixosConfigurations.well
nix flake show           # inspect exposed flake outputs
nixos-rebuild switch --flake .#well
```

`nix flake check` may print `unknown flake output 'modules'`; that is expected — the
dendritic `flake.modules` grouping also gets published as a flake output. Harmless.
